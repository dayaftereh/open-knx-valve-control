## Firmware isolation and fixed GPIO safety contract

Built isolated RP2040 image in tools/knx084_passive_rx_temp/
with src/main.cpp and platformio.ini.

- **GPIO0 -> STKNX U9 KNX_TX**: SIO output preloaded **LOW**, never set HIGH,
  repeated LOW reassertion about every 100ms. NO PIO KNX transmit
  program, no Serial1/UART0, no TPUart/GroupValueWrite, no output API.
- **GPIO1 <- STKNX U9 KNX_RX**: INPUT, CHANGE interrupt, raw timestamped
  rising/falling RX edge recorder with 4096-slot ring buffer.
  Every interval USB emits passive RXSTATS; permitted RXDUMP exports
  captured bus edges but never drives TP.
- **GPIO10..17 motor enables**, **GPIO18/19 common directions**:
  ALL SIO outputs set LOW in setup before serial initialization, and
  reassert LOW regularly. No motor drive/PWM/direction commands.
  All USB commands except STATUS, TEMPS, RXSTATS, RXDUMP, HELP refused.
- **GPIO8 TX / GPIO9 RX** use UART1/Serial2 at 115200 Baud to ATtiny3216
  U25 PA2 RX / PA1 TX. Every ~2.1s request a CRC-protected cached snapshot
  (8-byte request, 67-byte response, protocol KNX014).
  Parser enforces CRC16, sequence, response type and nine-channel
  flags/faults; return only T0..T3 with invalid data as temp_c=NA.
  Arduino-Pico SerialUART::availableForWrite() is Boolean and guarded
  with <=0, as proven in KNX041.

The firmware controls GPIO only **after application startup**. It
CANNOT guarantee electrical TX or motor LOW during power-on, BOOTSEL,
reset or brownout. The V1.2 TB6612 STBY pin is hardwired HIGH; there is
no independent motor STO. This is NOT certified hardware safety.

Raw STKNX KNX_RX edges from the capture were processed OFFLINE by
tools/knx084_passive_rx_temp/knx084_decode_capture.py using the
existing KNX070 TP1 parity/checksum/ACK decoder:
**4095 edges, 2047 physical active pulses, 27 frame groups;

1.3.40 -> 4/2/5 and 1.3.43 -> 4/2/0 / 4/2/1,

One defect was found in the HOST monitor schedule, not in
temperature data: the initial RXDUMP occurred too late, allowing
the 4096-slot ring to fill. An initial total of **1897 older edges**
were dropped while RXSTATS still counted all **6612** physical
edges. The serial RXDUMP itself is passive. This was corrected to
drain at connect and then every **8s**.

A later independent read-only COM8 STATUS / TEMPS / RXSTATS check
confirmed the same firmware running continuously with:

    KNX084 STATUS tx_low=1 motors_low=1 uart_ready=1
    snapshots=223 timeout=0 rejected=0 rx_edges=31680

At that time T0=15.19C, T1=14.88C, T2=14.75C,
T3=14.69C; flags=3 and fault=0 on every channel, with
ages 2-3s. GPIO0 and all ten motor output pins still read LOW.
RX counts were 15,840 rising and 15,840 falling.
The 4096-event timestamp ring was full (buffered=4095)
and accumulated 18,115 discarded OLD event timestamps during
unattended observation, as expected from its finite design.
This is a limitation of long-term waveform archival without the
live serial monitor, NOT evidence of a KNX bus failure.
The counters continue monitoring even when the ring is full;
the final host tool drains the ring immediately on connection
and every eight seconds afterwards.

To avoid losing complete raw telegram history over hours, run
the monitor continuously or add a bounded rolling-buffer or
external logging improvement in a future slice. No further
firmware reflashing was necessary for this first temperature
and RX verification.
